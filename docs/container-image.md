# Capykit MCP container image

Capykit publishes the read-only MCP server as `ghcr.io/driftward-llc/capykit`.
The container recipe is generated by `scripts/container-image.mjs` so the
repository does not need to keep generated Dockerfile content in source control.

## Build contract

The runtime image uses a pinned Node.js 22 slim base:

```text
node:22.18.0-bookworm-slim@sha256:0d130e2ee18e88e1561375276daced6bff032539200173f2daf48c2e33f38ff5
```

Builds must run after the package build has produced `dist/`:

```bash
npm ci
npm run build
node scripts/container-image.mjs print-containerfile > /tmp/capykit.Containerfile
docker build --pull=false -f /tmp/capykit.Containerfile \
  -t ghcr.io/driftward-llc/capykit:0.0.0 \
  -t ghcr.io/driftward-llc/capykit:sha-$(git rev-parse --short=12 HEAD) \
  .
```

Use immutable, versioned tags for published images. Do not publish `latest` as a
release contract until the release process explicitly defines mutable tag policy.

## Runtime hardening

The generated image:

- runs as the non-root `node` user provided by the pinned base image;
- installs production dependencies with `npm ci --omit=dev --ignore-scripts`;
- copies only package metadata, `dist/`, schemas, README, and LICENSE into the
  runtime filesystem;
- declares `/registries` as the registry mount point;
- starts `node dist/mcp.js --registry /registries/registry.json` by default;
- includes a container health check that loads the MCP module and constructs the
  server without opening a transport or probing external services.

Run with a read-only root filesystem and a read-only registry mount:

```bash
REGISTRY_MOUNT="type=bind,source=$PWD/examples/all-interfaces.registry.json"
docker run --rm --read-only --network none \
  --mount "$REGISTRY_MOUNT,target=/registries/registry.json,readonly" \
  ghcr.io/driftward-llc/capykit:0.0.0
```

The v0.1 MCP transport is stdio, so `--network none` is appropriate unless a
future transport explicitly requires network access.

## Resource guidance

For the v0.1 read-only stdio server, start with:

- memory limit: 256 MiB;
- CPU limit: 0.25 vCPU for small catalogs, 0.5 vCPU for larger catalogs;
- process limit: one MCP server process per container;
- registry mount: a single JSON registry or generated aggregate mounted read-only
  at `/registries/registry.json`.

Increase memory before CPU if schema validation or large catalog loading becomes
the bottleneck.

## Credential policy

No credentials are baked into the image. Registry files must contain credential
references only, not credential values. Runtime registry mounts should be
read-only and supplied by the orchestrator, not copied into the image.

Before publishing, run:

```bash
npm run check:secrets
```

Also inspect the generated Containerfile and image metadata:

```bash
node scripts/container-image.mjs print-containerfile
node scripts/container-image.mjs print-metadata 0.0.0
```
